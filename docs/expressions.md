# Expressions

Each construction here replaces one familiar expression, e.g. `a >= b` or `x / y`, where the hard part is an exact FP32 result. Constructions that replace a loop are in [patterns.md](patterns.md), and choices that change what the user sees are in [behavior-choices.md](behavior-choices.md). `f(x)` means `Math.fround(x)`, and `[condition]` means 1 when the condition holds and 0 otherwise. The functions are in the runtime, [src/runtime/numeric-ui-core.ts](../src/runtime/numeric-ui-core.ts), unless a row names another place. numeric-library is [lab/ui-exploration/numeric-library](../lab/ui-exploration/numeric-library/README.md), a tested library of builder functions outside the runtime, to import or to copy from.

## Decision bits

A score isn't automatically a decision. A rectangle edge may produce `0.3`, which is useful for smooth math but invalid for `open`, `focused` or `maximized`: passing it onward as state would give a partly maximized window. Make the bit exact at the moment a score becomes a decision, e.g. click ownership, focus or visibility flags, and keep positions, sizes, opacity, scale and springs at full precision. Once a bit exists, products of bits, and sums of bits that can't be 1 at the same time, stay exact bits, so the constructions below are needed only where a score first becomes a decision.

`emitCompare(circuit, a, relation, b)` in numeric-ui-core.ts is the default. It picks one of the forms below from both operands' declared ranges, which must be finite. The first row of the table above has the costs, and [execution-model.md](execution-model.md#comparisons) the full cost table. Integer bits and a sign cascade return the same bits, so a comparison that became a sign cascade doesn't show in any result: count `circuit.roundingPoints()` by kind after building, e.g. comparing an index read within 0..16,384 without a declared grid adds 15 `'sign cascade'` entries, and `circuit.assumeGrid(read, 1)` before the comparison gives 2 `'integer bit'` entries instead ([rounding points](execution-model.md#rounding-points)). The three forms, from cheapest to most general:

- **Integer bits.** When the score is an integer count, `relu(score) - relu(score - 1)` is already the exact bit of `score >= 1`, since an integer can't land strictly between 0 and 1, e.g. an element is visible when `baseVisible + the number of selected slots that reveal it` is at least 1. This form needs no special constant, trains with the plain reference backward pass, since for a fractional score inside 0..1 the same expression is the identity ramp, and stays exact in narrower formats like bfloat16 as long as the integers fit the mantissa (validated in [lab/event-window/integer-bits.test.ts](../lab/event-window/integer-bits.test.ts)). On a grid, `emitCompare` builds `a >= b` as `relu(1 - relu(-D))` on the integer `D = (a - b) / grid`.
- **The boolean atom.** When the score is continuous and lands in 0..1, e.g. a clamped hit distance, adding 8,388,609 and then subtracting it rounds the score at 0.5. The atom is one operation and takes any score in 0..1, but it only works in FP32: the executor has to keep the stored FP32 evaluation, and `backpropagateReference` throws on the atom unless the caller passes `{booleanGradient: 'straight-through'}`. `emitCompare` ends with an atom when passed `{endWithBoolean: true}`.
- **The sign cascade.** When the decision compares two continuous values and must be exact for any finite difference, keep `d = f(a - b)` as its own operation, which is 0 exactly when `a === b` and otherwise has the sign of `a - b`. Then alternate multiplying its positive part by a power of two (exact in FP32: the exponent shifts and the mantissa is untouched) with clamping, until every positive `d`, down to 2^-149, has reached at least 1, so a last ReLU product, e.g. `relu(1 - lifted)`, is an exact bit. Every stage computes an exact value, so the bit stays right when an executor evaluates a stage in float64 or adds its terms in another order, as long as each stage stays its own operation. The boolean atom is a one-operation shortcut for this construction, not a necessity.

An integer bit written as `relu(score) - relu(score - 1)` can stop being exact inside a sum that reads it. The bit is an ordinary affine sum of 2 ReLU terms, and the builder copies an ordinary affine sum of fewer than 4 terms into the sums that read it, so when those ReLUs hold large values, the reader's running FP32 sum rounds. E.g. the sum rounds with fractional weights over ReLU values up to 8,192, or with a 2^18 coefficient that pushes partial sums past 2^24 ([the two cases](../lab/ui-exploration/README.md#where-it-got-awkward)). Keep such a bit as its own `roundAffine` wire. `emitCompare`'s bits end with a ReLU product or a boolean atom, which the builder never copies into a reader.

An exact bit is exact for the FP32 values it compares, not for the float64 arithmetic of the JavaScript it replaces. E.g. a column count computed as `f(f(1732 - 24) × f(1 / 244))` is 6.9999995, one FP32 step below 7, where float64 gives exactly 7, so an exact bit of `columns >= 7` is 0 where float64 JavaScript gives 1: the reciprocal rounds before any comparison runs. A [threshold count](../lab/ui-exploration/guide/patterns/threshold-counts.md) compares the width with each threshold instead and avoids the reciprocal.

## Magnitude safety

FP32 holds every integer exactly only up to 2^24 (16,777,216), and above that, neighboring values are 2, then 4 apart. Macros that subtract inside their expansion lose precision past that point, so keep the operands of clamps, `emitMinimum` and `emitMaximum` under 2^23 (about 8.4 million), and keep a clamp's operand as its own `roundAffine` wire when it's a small affine sum that can hold a fraction ([Clamping](execution-model.md#clamping)). Where a min, max or clamp must be exact for fractional operands, use `emitMinimumExact`, `emitMaximumExact` or `emitClampExact`. Pixel-space UI, with coordinates in the thousands and scores in 0..1, sits far inside this limit unless a construction scales values up on purpose, e.g. multiplies a score by 100,000 to sharpen it. `emitSelect` at a condition of exactly 0 or 1 returns the chosen finite operand exactly at any magnitude, and `emitMultiply` equals one FP32 product for finite operands. [execution-model.md](execution-model.md#macro-contracts) has every macro's contract and failing values. Declared ranges and grids are promises the builder trusts, e.g. a false grid turns an integer bit into a fraction ([declarations](execution-model.md#declarations)).

## Dynamic division

Two constructions divide by a runtime value. Both are in lab folders, not in the runtime:

- lab/ui-exploration/numeric-library's `emitReciprocal(x)` reads a starting estimate from threshold bits, one per octave of the divisor's declared range, then runs Newton steps `e × relu(2 - x × e)`, which square the relative error at each step. `emitDivide` multiplies the result by the numerator. The `x / y` row of the table above has the costs, the error bounds and the range that the divisor needs.
- For `Math.floor(n / m)` with whole numbers n and m, where m is a runtime value with few possible values, compute `round(n × (1/m) - (m - 1) / (2m))`, reading both constants through the one-hot of m, as [life-calendar.ts](../lab/ui-exploration/codegen/life-calendar.ts) does for a week number. The quotient's fractional part is a multiple of 1/m, so rounding can't give the wrong integer ([loops, other uses](../lab/ui-exploration/guide/sections/loops.md#other-uses)).
